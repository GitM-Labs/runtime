## Provisional schema position for the Oct 19 review

Keep **one shared core for workload, logical work, resource demand, provenance and genuine dependencies**. Put family 3's spatial placement, stage initiation interval, buffers and routes in a **sibling plan schema**, joined to the same logical graph by stable region IDs. Family 2 may use the core with a compiled-region adapter and tiered transfers; decide only after seeing a Neuron compiler output and trace. This is a provisional design choice, not a measured superiority claim.

If we force a single kernel-shaped schema onto spatial execution, we will count on-chip streaming as HBM rereads, sum overlapped stages, attribute fictitious launch loss, and recommend impossible stream/capture interventions. If we split everything, logical op names, workload regimes and provenance drift across families and cross-platform comparisons become unverifiable. I would reverse the sibling-plan decision if an SN40L compiler/trace pair maps stage residency and steady-state time to the existing `PredictedNode` and dependency representation without special rules or systematic residuals; I would split more of family 2 if a Neuron NEFF likewise cannot preserve logical region attribution. These are falsifiable criteria for requirements v1.

## Measured GPU lowering boundary

The Qwen experiment shows that even within family 1, a canonical node is not necessarily one physical kernel. The actual Transformers backend issues separate q/k/v projections, normalization/rotary/residual/cache operations and KV-head expansion around SDPA. Classify logical geometry as invariant, backend selection and mapping as family-parameterized, and the concrete fusion/materialization/launch pattern as backend-specific. A measured profile is evidence for its own backend, not a universal GPU lowering.

Correct the launch assumption precisely: dense `predict_graph` calls `roofline` with its zero-launch default. GLM generally passes one serial launch. Neither a global one-launch-per-node rule nor the observed profiled kernel count is a justified cross-family boundary model. The existing CLI already labels the peak calculation as a floor, not a latency target. A sum of node costs becomes a whole-step bound only with valid traffic, rates and serial-schedule assumptions.
