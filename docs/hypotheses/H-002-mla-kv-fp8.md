## Claim

On the team's 8xMI355X Kimi K2.5 deployment at TP8, adding `--kv-cache-dtype fp8` reduces decode inter-token latency (ITL) by 7.08% at the loop's headline point (`rag`, 64 concurrent), with a derived range of -1.97% to 16.32%. The low end of that range is a regression. The range assumes the bf16 kernel runs inside the planner's efficiency band, which its 64-workgroup grid may not; the run measures that kernel before any fp8 sample and re-registers the band if it falls outside (Experiment step 2). The bf16 and fp8 arms run different AITER kernels, so each end of the planner's efficiency band is independent. The fp8 arm also runs four kernels the bf16 arm does not: three per layer (query concat-and-quantise, an 8 to 16 head pad, a split-KV reduce) and one per step (AITER's schedule build), and its decode kernel writes split-KV partials the bf16 kernel does not. On the measured basis that is 0.491 ms per step of launches at every end of the band, plus the partial writes, priced with the fp8 kernel at its efficiency (0.100 ms at the mean). The cache-read saving in ms grows with the cached tokens read per step and does not shrink with tensor parallelism. The fixed cost does depend on TP: at TP4 (16 heads per rank) the bf16 arm already runs the padded asm path, no fp8-only kernel is extra, and the mean saving is 1.631 ms against 1.040 ms at TP8. That row is conservative by about 0.7 points: the bf16 arm's non-persistent fallback launches one fill kernel per layer that the fp8 arm does not, which is not priced (worked under "What it adds").

This is the lever the loop runbook already plans for its `e8` arm (`INTERVENTION='--kv-cache-dtype fp8'`). This spec registers the prediction before that run.

## Mechanism

vLLM resolves `--kv-cache-dtype auto` from the checkpoint (`engine/arg_utils.py:2069-2071`, calling `utils/torch_utils.py:506-524`):

- A modelopt `kv_cache_scheme` of static 8-bit float resolves to fp8 (`:452-467`).
- Anything else stays `auto`, which becomes the model dtype (`:494`, `:524`).

`moonshotai/Kimi-K2.5` is compressed-tensors with `kv_cache_scheme: null`, so its cache is bf16. `nvidia/Kimi-K2.6-NVFP4` declares a static fp8 scheme, so its default is already fp8. The applicability check refuses it.

| | Bytes per cached entry (576 elements) | Bytes per token, 61 layers |
|---|---:|---:|
| bf16, what K2.5 stores by default | 1,152 | 70,272 |
| Generic fp8, one scale per layer | 576 | 35,136 |

The generic fp8 layout stores the whole entry (512 latent plus 64 RoPE) at one byte. `model_executor/layers/attention/mla_attention.py:438` sets `head_size = kv_lora_rank + qk_rope_head_dim`, and the cache spec holds one KV head of that size in the cache dtype (`:1207-1220`). Scales are per tensor only (`model_executor/layers/quantization/kv_cache.py:124-127`).

MLA keeps one latent per token shared by all 64 heads, so every TP rank holds and reads the whole cache. At decode the attention core is memory-bound and its bytes are the cache read, so halving the element width halves that node's floor.

Two more things change with the flag at v0.29.0. Neither is in the cache bytes:

- **The query.** With an fp8 cache vLLM concatenates the query's latent and RoPE parts and quantises them to fp8 in one op before attention (`mla_attention.py:945-950`, op at `:1415-1445`; on the loop's default config it runs as one compiled kernel, see "The extra kernels" step 2), because every MLA backend priced here inherits `supports_quant_query_input = True` (`:3145`). The bf16 arm hands the backend the two parts as a tuple instead (`:951-952`). The query scale is the k scale, which is 1.0 for this checkpoint (`kv_cache.py:107-111`, `:129-136`). At TP8 Kimi has 8 heads per rank. AITER's Triton-Gluon kernel takes the bf16 tuple at 8 heads directly (`v1/attention/backends/mla/rocm_aiter_mla.py:1770-1771`) but cannot serve an fp8 cache, so vLLM pads the fp8 query to 16 heads with `repeat_interleave` before AITER's asm kernel (`:1334-1353`, `:1904`, `:1293-1304`). Both are priced below with the fp8 arm's other extra kernels.
- **First-chunk prefill.** On gfx950 an fp8 cache also turns on AITER's fp8 asm prefill for prefills with no cached context. It casts q, k and v from bf16 to fp8 at scale 1.0 and runs `mla_prefill_ps_asm_fwd` then `mla_reduce_v1` (`rocm_aiter_mla.py:85-101`, `:1479-1488`, `:1503-1567`, `:1700`). A batch falls back to the bf16 path whenever any prefill in it has context (`:1676-1688`; the chunked-context metadata is None only when no prefill has any, `mla_attention.py:1917-1919`). Context is cached tokens or the prompt's own earlier chunk: a prompt longer than the token budget left in its step is chunked, and every chunk after the first runs bf16. Prefix caching is on by default (`config/cache.py:138`) and a cached prefix counts as context (`mla_attention.py:2446-2448`), so a prompt whose first 16-token block (the default KV block, `config/cache.py:79`) is already cached runs bf16 prefill, and so does every prefill batched with it or with a later chunk. This changes numerics and TTFT, not decode ITL. The correctness gate must reach it on purpose (Gates), and the TTFT gate watches it. On the pinned v0.29.0 that prefill is also wrong at 8 heads per rank: `get_mla_padded_q` pads 8 to 16 heads with `repeat_interleave` (`:1302-1304`, heads 0,0,1,1,...,7,7) and `_mla_fp8_prefill_attn` copies back `out_3d[:, :8]` (`:1634`), which holds heads 0,0,1,1,2,2,3,3, so heads 4 to 7 are lost on every fp8 prefill with no context (vllm-project/vllm#60907, merged to vLLM main on 2026-10-14 as `e534024` and in no tagged release, the newest being v0.31.0 of 2026-10-05, so the pinned v0.29.0 image keeps the bug; it names #51040, which v0.29.0 ships, as the cause, and measures GSM8K 0.027 before and 0.933 after on Kimi-K2.6 TP8 with an fp8 cache). Known blocker: see Gates.

## Total overhead versus the recoverable part

At the headline point, the attention core's cache read above an fp8 cache is 1.223 ms of floor per step, or 1.631 ms on the measured basis (floor divided by the planner's mid-band efficiency, 0.75). That is the total overhead.

The intervention can recover all of those bytes, less what its own extra kernels cost. How much time comes back depends on whether the kernel changes:

- **MI355X keeps the backend, not the kernel.** With `VLLM_ROCM_USE_AITER=1` and `VLLM_ROCM_USE_AITER_MLA` at its default (on), `ROCM_AITER_MLA` is first for MLA (`platforms/rocm.py:469-479`, `_aiter_ops.py:1953-1956`). At 8 heads per rank it picks the kernel by cache dtype (`rocm_aiter_mla.py:1334-1353`):
  - bf16: AITER's Triton-Gluon `_mla_gluon` in its `bh16bn64` regime, a 16-row head block with heads 8 to 15 masked (`aiter:aiter/ops/triton/gluon/mla_gluon.py:56-57`, `:883`, `:1029`). vLLM calls it at `rocm_aiter_mla.py:1767-1799` with `min_kv_seq_len = 1` for plain decode (set at `:1090`, passed at `:1798`), so the split count is max(1, min(256 / 64, ceil(1 / 64))) = 1 (`mla_gluon.py:943-945`). With one split, stage 1 writes the output directly and returns before the reducer `_mla_softmax_reducev_kernel` (`:1080-1082`, defined `:722-723`). The builder makes no persistent schedule for Gluon (`rocm_aiter_mla.py:1037-1051`). One kernel per layer.
  - fp8: the quantised query is padded to 16 heads, AITER's persistent schedule is built once per step by `get_mla_metadata_v1` (`rocm_aiter_mla.py:1037-1077`), then the asm kernel `mla_a8w8_qh16_qseqlen1_gqaratio16_ps` runs, then `mla_reduce_v1`, every layer (`aiter:aiter/mla.py:506-581`, `:656-694`; `aiter:csrc/py_itfs_cu/asm_mla.cu:867-905`; `aiter:hsa/gfx950/mla/mla_asm.csv:9`). AITER's fallback away from the persistent kernel at 32 or more sequences applies to bf16 only (`aiter:aiter/mla.py:222-267`). vLLM calls it at `rocm_aiter_mla.py:1904-1976`.

  Two kernels, so each end of the band is independent, as on Hopper. The kernel's time still halves at the mean.

  **The bf16 Gluon grid is small, so the band's bf16 efficiency is checked before any fp8 sample.** With one split per sequence, Gluon's grid is (sequences, splits, qlen) = (64, 1, 1), 64 workgroups (`mla_gluon.py:1026`). Each workgroup holds about 160 KiB of LDS (`rocm_aiter_mla.py:150`; the two 64-token bf16 KV buffers alone are 2 x 512 x 64 x 2 B = 128 KiB, `mla_gluon.py:416-418`, plus the query buffers, `:358-360`), and gfx950 has 160 KiB per CU (AMD's CDNA4 figure, not in source), so one workgroup runs per CU: 64 of MI355X's 256 CUs. AITER's own comment sizes one MI350 wave as about 256 workgroups (`:938-942`), which vLLM's `min_kv_seq_len = 1` defeats. To run at `eff_lo` (0.55), each workgroup must stream one sequence's 4,352 x 1,152 B = 5.01 MB per layer in 72.9 µs, 68.8 GB/s, which is 2.2 times an even 256-way share of 8 TB/s (31.3 GB/s). Whether one CU sustains that is not in source. If it does not, the bf16 core runs below the band, part of the fp8 arm's gain is leaving an under-filled kernel rather than halving bytes, and the registered hi end is not an upper bound. The fp8 arm's persistent asm kernel runs on all 256 work slots (`aiter:csrc/kernels/mla/metadata/v1_2_device.cuh:847`, `:901-903`), so the band still applies to it. The run therefore measures the bf16 kernel first (Experiment step 2): if `_mla_gluon` is outside the band's bf16 times, the band is re-derived from the measured time and re-registered before any fp8-arm sample.
- **Blackwell keeps the backend.** `FLASHINFER_MLA` is first on sm100 and stores both dtypes (v0.27.1 `platforms/cuda.py:118-128`, `v1/attention/backends/mla/flashinfer_mla.py:124-130`). Whether its fp8 path is the same kernel was not read, so it is priced as a switch, the wider band.
- **Hopper switches the kernel.** `FLASH_ATTN_MLA`, first on sm90 (v0.27.1 `platforms/cuda.py:136-143`), stores no fp8 (`flashattn_mla.py:45-49`), so fp8 moves the core to `FLASHMLA` (`flashmla.py:49-55`). The old and new kernels may then land at different efficiencies. In the worst case in the band, the kernel's time falls by only 13.6% instead of 50%.

What the intervention does not recover: the core's launch floor and its output traffic. What it adds: the kernels the fp8 arm runs and the bf16 arm does not.

- **MI355X, 8 heads per rank (TP8).** The concat-and-quantise, the 8 to 16 head pad and `mla_reduce_v1` every layer, `get_mla_metadata_v1` once per step, and the split-KV partials stage 1 writes every layer: 0.443 ms of floor per step at the headline. The launches cost 0.491 ms on the measured basis at every end; the writes are priced inside the fp8 kernel, 0.100 ms at the mean (worked below).
- **MI355X, 16 heads per rank (TP4), or a head count 16 is not a multiple of.** No fp8-only kernel. The bf16 arm takes the padded asm path too: it concatenates the tuple (`rocm_aiter_mla.py:1892-1893`), pads the same way, builds the same schedule (`:1037-1051`) and reduces: `mla_reduce_v1` on the persistent path, or Triton `_fwd_kernel_stage2_asm` where AITER falls back to the non-persistent kernel (`aiter:aiter/mla.py:222-267`, `:469`, `:684-694`). At 64 sequences AITER does fall back for bf16 (the fallback applies to bf16 only, from 32 sequences, `:222-267`) and picks 4 KV splits per sequence for occupancy (`:150-185`): 256 partials of the same 32,832 B as the fp8 arm's tiles. That non-persistent path also fills its `valid_split_count` buffer with `torch.full` on every call (`:408-409`), one launch per layer that the persistent fp8 arm, whose buffers are `torch.empty` (`:607-616`), does not make (its other fill, `get_meta_param`'s `torch.arange` at `:215-217`, sits behind an `lru_cache`, `:125`, keyed on the padded batch and vLLM's whole index buffer, `rocm_aiter_mla.py:452-454`, `:994`, so it runs once, not per layer). So at TP4 the fp8 arm launches 61 fewer kernels per step than the bf16 arm, 61 x 2 µs / 0.75 = 0.163 ms on the measured basis, which is not priced (the derivation prices only kernels the fp8 arm adds): the TP4 row understates the saving by about 0.7 points (2.22% / 7.54% / 13.31% with it). In the other direction, the two arms' partial bytes match at the aligned 4,352 tokens, but over the headline window the fp8 schedule averages 300.3 tiles (worked below) against bf16's 256; that difference, about 44 tiles x 32,832 B x 61 layers = 0.011 ms of floor per step, is not priced either. Net, the row is conservative.
- **H200, default pair.** The concat-and-quantise alone, 61 x 2 µs / 0.75 = 0.163 ms. FA-MLA unpacks the bf16 tuple without a kernel (v0.27.1 `flashattn_mla.py:328-329`).
- **H200 pinned FlashMLA, and B200.** None. The bf16 backend concatenates the tuple itself (v0.27.1 `flashmla.py:277-278`, `flashinfer_mla.py:273-275`), and the fp8 arm's fused concat-and-quantise replaces that copy.

A second benefit, twice the cache capacity per rank, is real but is not a per-step latency effect and is not part of this prediction.

## Intervention

`--kv-cache-dtype fp8` (EngineArgs `kv_cache_dtype = "fp8"`). No weight change. Rollback is a server restart without the flag. On the loop pod that is `arm.sh`, which restarts in-pod.

## Applicability conditions

Checked in code before a candidate is emitted (`_h002_applies`), each with a reason when it fails:

1. The model uses MLA (`kv_lora_rank > 0`). A GQA cache splits across TP ranks, and the effect would divide by TP.
2. The model is *dense* MLA: no DSA indexer on any layer. On sparse MLA (GLM-5.2) an fp8 cache takes the `fp8_ds_mla` layout on a sparse backend, 656 B per entry with per-128 fp32 scales (`mla_attention.py:349-362`, `:1218-1220`), which is not the 576 B this derivation prices.
3. The executed cache is bf16 or fp16, and not already any fp8 flavour (`fp8`, `fp8_e4m3`, `fp8_e5m2`). An explicit `serving["kv_cache_dtype"]` wins. Otherwise it is the catalogue's `kv_dtype`, which records what `auto` resolves to.
   - `kv_cache_dtype_skip_layers` must be empty. vLLM keeps the named layers at the model dtype (`engine/arg_utils.py:1299`, applied to MLA at `mla_attention.py:452-456`), and this derivation prices all 61 layers in fp8. A partly fp8 cache is a different prediction (rejection 4), so it is refused.
4. The attention kernel is one the derivation priced. With no `attention_backend` in the serving config that is vLLM's default pair for the arch: Hopper `FLASH_ATTN_MLA` to `FLASHMLA`, Blackwell `FLASHINFER_MLA` both sides, CDNA4 `ROCM_AITER_MLA` both sides.
   - CDNA4 needs `VLLM_ROCM_USE_AITER=1` and `VLLM_ROCM_USE_AITER_MLA` left on (its default). With either off ROCm lists `TRITON_MLA` first (`platforms/rocm.py:469-479`), which is not priced; a pinned `ROCM_AITER_MLA` is honoured without either flag (`platforms/rocm.py:628-642`, `_aiter_ops.py:134-146`), but then runs with the rest of AITER off, which is not the loop env the derivation prices, so that is refused too, with a reason that says so. vLLM treats each flag as on only for `1` or `true`, any case (`envs.py:1235-1237`, `:1282-1283`), and so does the check.
   - `VLLM_ROCM_AITER_MLA_ASM_PADDING` (`envs.py:1293-1298`) must leave the bf16 arm on the kernel `auto` picks. `use_gluon_decode` (`rocm_aiter_mla.py:1334-1353`) reads the mode only under 16 heads per rank: `auto` takes Gluon when 16 is a multiple of the head count, `gluon` whenever a Gluon build exists, `asm` never. So at 8 heads per rank `gluon` selects the priced kernel and is accepted, while `asm` moves the arm to the padded asm path (`:1348-1349`) and is refused; at a head count 16 is not a multiple of, it is the other way round. The loop sets only `VLLM_ROCM_USE_AITER`, so it runs `auto`.
   - An explicit backend is accepted only if it is one of the pair. Forcing `FLASHMLA` on the bf16 side (the H200 pinned-backend arm) is accepted and priced with the switch band, because FlashMLA runs different kernels for bf16 and fp8 (see Experiment). `auto`, vLLM's spelling for automatic selection (`config/attention.py:162-164`; `--attention-backend` goes through the same validator, `engine/arg_utils.py:2496-2498`), is no pin and is accepted as the default pair. Anything else is refused with the reason.
5. The step is decode, with one query token per sequence, on one TP group, and no decode context parallelism. Speculative decoding (EngineArgs `speculative_config`, `spec_method`, `spec_model` or `spec_tokens`, `engine/arg_utils.py:692-695`, or gitm's `num_speculative_tokens` knob) makes verify steps carry several query tokens per sequence, which turns Gluon decode off (`rocm_aiter_mla.py:1339-1340`). `decode_context_parallel_size` above 1 multiplies the decode heads per rank (`:1426-1428`) and splits the cache across ranks (`v1/attention/backends/utils.py:1091-1100`). `data_parallel_size` above 1 (or `ShardingConfig.dp`) steps every DP group together on their combined token count (`forward_context.py:80-99`, `:116-125`), which the one-group step priced here does not do. All three are refused with the reason.
6. Decode replays one full graph at the batch. The extra kernels are priced at the planner's graph-replay launch, 2 µs; eager launches are nearer 5 µs, which moves the whole band (Sensitivity). So the check refuses:
   - `enforce_eager` on, read as vLLM reads it: `ModelConfig` is a pydantic dataclass (`config/utils.py:51-74`, `config/model.py:123-124`, `:241`), so `true`, `1`, `yes`, `on`, `t` and `y` in any case count as on. vLLM then sets `cudagraph_mode` to NONE (`config/vllm.py:1370-1376`).
   - `VLLM_USE_BREAKABLE_CUDAGRAPH=1` (read as `1` only, `envs.py:757-759`), which runs MLA attention eagerly between graph segments (`mla_attention.py:1319`, `compilation/breakable_cudagraph.py:319-322`) and forces compilation mode NONE (`config/vllm.py:725-728`). Kimi K2.5 is not on vLLM's default list for it (`:75-93`), so only the explicit flag turns it on.
   - `compilation_config.cudagraph_mode` NONE or PIECEWISE (a dict or the `--compilation-config` JSON string, `engine/arg_utils.py:815-819`; names in any case or enum values, `config/compilation.py:53-63`, `:870-876`). NONE runs no graph; PIECEWISE runs attention outside its graphs. With no explicit mode, `optimization_level` 0 or 1 supplies NONE or PIECEWISE (`config/vllm.py:255`, `:278`); the default level 2 supplies FULL_AND_PIECEWISE (`:301`, `:419`).
   - A compilation mode other than VLLM_COMPILE with the default FULL_AND_PIECEWISE cudagraph mode: that mode needs piecewise compilation, so vLLM overrides it to NONE (`config/vllm.py:1468-1480`; Kimi K2.5 is not on the breakable-cudagraph list, `:75-93`). `compilation_config.mode` 0, 1 or 2 (`config/compilation.py:37-50`), `TORCH_COMPILE_DISABLE=1` (which forces mode NONE, `config/vllm.py:1390-1395`) and `-O0` with an explicit FULL_AND_PIECEWISE (mode NONE, `:1431-1435`) are all refused. FULL and FULL_DECODE_ONLY need no compilation, but mode NONE is refused with them as well, under applicability 7.
   - A `compilation_config` that is not a dict or JSON object, such as autoresearch's `compilation_config: 3` (`gitm/agents/autoresearch.py:235`, `:422`). vLLM v0.29.0 no longer takes the `-O` level there (`engine/arg_utils.py:815-819`; levels are `optimization_level`), so it is refused with the reason instead of crashing the proposal, which would lose every other hypothesis with it. The same goes for an `attention_config` that is not one, a string that is not JSON, a `cudagraph_mode`, `mode`, `custom_ops`, `cudagraph_capture_sizes` or `backend_per_kind` value vLLM would not parse (`config/compilation.py:853-876`, `config/attention.py:176-199`), and a count that is not a positive int (`max_num_batched_tokens`, `max_num_seqs`, `max_cudagraph_capture_size` and the three parallel sizes, `config/scheduler.py:49`, `:63`, `config/parallel.py:126-129`, `:349`).
   - `prefill_context_parallel_size` above 1, which ROCm overrides to PIECEWISE (`platforms/rocm.py:902-913`); only ROCm does, so on CUDA it is accepted.
   - `kv_transfer_config`: a layerwise KV connector gets the same override (`config/vllm.py:1556-1581`), and no connector's transfers are priced, so any is refused.
   - A batch above the largest captured size, which dispatches to no graph (`v1/cudagraph_dispatcher.py:274-281`). Explicit `cudagraph_capture_sizes` (top level or inside `compilation_config`) keep the sizes at or under `max_num_batched_tokens`, dropping the rest (`config/vllm.py:2096-2104`). Otherwise `max_cudagraph_capture_size`, else vLLM's default ceiling, min(2 x `max_num_seqs`, 512; 1024 on Blackwell) (`:2003-2016`), is capped at `max_num_batched_tokens` (`:2092-2093`) and, unless that budget is itself captured (`:2131-2136`), rounded down to the capture grid, 1, 2, 4, then 8s below 256 and 16s from 256 (`:2117-2129`, `:2160-2182`): a `max_cudagraph_capture_size` of 300 captures up to 288. `max_num_seqs` defaults to 1024 on every priced SKU (`engine/arg_utils.py:2698-2717`); the loop serves `--max-num-seqs 256`, so its ceiling is 512.
7. The fp8 arm's query concat-and-quantise compiles to one kernel ("The extra kernels", step 2). The check refuses what makes it two: `compilation_config.custom_ops` enabling the op (`all`, or `+mla_decode_concat_quant_fp8` without `-mla_decode_concat_quant_fp8`, `custom_op.py:285-311`), a compilation mode of NONE (`mode` 0, `-O0`, `TORCH_COMPILE_DISABLE=1`, with any cudagraph mode) and a backend other than Inductor, because vLLM then adds `all` itself (`config/vllm.py:1444-1451`), or with `none` given leaves `forward_native` uncompiled (`custom_op.py:222-225`), and the op runs as `torch.cat` plus AITER's quantise, 61 more launches than priced.
8. The mean predicted step reduction clears the measured noise floor (`HypothesisProposer(noise_floor=...)`).

These checks run only where a caller supplies the serving config. Nothing builds `Workload.serving` in production yet: the proposer is not wired into the loop, and nothing maps the pod's env or `arm.sh`'s extra arguments into it, so only the tests construct one. The reference config, built by hand from `deploy/k8s/mi355x-kimi-loop.yaml` (the `vllm serve` flags and `VLLM_ROCM_USE_AITER=1`) plus each arm's extra arguments in `scripts/kimi_loop/arm.sh`, gives: arms A and B accepted; arm C (`--enforce-eager`, `arm.sh:37`) refused on eager, as the correlation arm should be; arms I and L (`--kv-cache-dtype fp8`) refused as already storing an fp8 cache, which is right from the baseline the hypothesis is proposed on. Whoever wires the proposer into the loop builds this dict from the same two files.

## Expected effect, derived before any run

**Observable.** ITL p50 is `median_itl_ms` from `vllm bench serve` (vLLM v0.29.0): the median over every per-token inter-token gap of every request, pooled. The client appends one gap per streamed chunk after the first (`vllm/benchmarks/lib/endpoint_request_func.py:241`), the run concatenates every request's gaps (`vllm/benchmarks/serve.py:620`) and takes `np.median` of them (`:756`). The load is a staggered pipeline. `vllm bench serve` at its default request rate (inf) queues every request at once (`vllm/benchmarks/serve.py:458-459`) behind a 64-wide semaphore that each request takes and releases on its own (`:968-976`), and every request has the same 4,096 / 512 lengths. The first 64 are admitted two per prefill step (`--max-num-batched-tokens 8192`), over 32 steps; once decodes share the step the second prompt of a pair is cut to the budget left and its tail runs a step later, so the sequences in flight are spread by up to about 40 tokens; each then decodes 511 steps (its first output token comes from prefill) and, as it finishes, its slot goes to the next request, whose prefill shares a step with the other sequences' decodes. The stagger therefore persists: every request runs a period of about 512 steps, and about one step in 14 carries a prompt, or a cut prompt's tail, beside the other sequences' decodes (counted below). Every sequence in a step has nearly the same cache length, walking from 4,097 to 4,607 tokens over its 511 decode steps, so the median gap is a decode-only step at batch 64, the quantity derived here. It is measured at the headline operating point (`rag` 4096/512, 64 concurrent, TP8) with the command below. The contract in tree, `experiments/contracts/h002-kv-fp8-mi355x.yaml` (the Harness v1 rewrite), registers this band but judges GuideLLM's `itl_ms_p50` with `reject_if_effect_below: 0.0` (`gitm/experiment/evaluate.py:338` rejects when the interval's upper bound is under it), not this observable and not rejection 1's threshold; a `vllm bench serve` contract matching this section (`H-002-rag-c64.yaml`) is a draft on branch `tarun/oct19-drafts`, not in tree. Until the two are reconciled (an open question for Isaiah and Tarun), the in-tree contract is what the evaluator runs. One seed per sample, so no prompt repeats within a run:

`median_itl_ms` is reported whatever `--metric-percentiles` lists.

`--num-prompts 1216` is 1,216 / 64 = 19 periods. Two 4,096-token prompts beside 62 decodes are 8,254 tokens against the 8,192 budget: the scheduler serves the running requests first and cuts a waiting prompt to what is left (`v1/core/sched/scheduler.py:550`, `:954`, `:998`), so the second prompt of a pair is cut and its tail runs in the next step, with context. Stepping that rule over the run, a freed slot refilled in the following step, gives 9,769 steps, of which 708 carry prompt tokens and 9,061 are decode-only. The decode-only steps take 9,061 x 14.69 ms = 133 s at the predicted baseline step. The prompt-carrying steps hold 1,216 x 4,096 / 8,130 = 613 full steps' worth of prompt tokens beside 62 decodes; at the planner's floor for such a step, 69.3 ms, divided by 0.75, that is 613 x 92.4 ms = 57 s, plus about 95 x 14.69 ms = 1 s for the rest of those steps. A run is about 190 s. `chat` (`H-002-chat-c64.yaml`) uses `--random-input-len 1024 --random-output-len 256 --num-prompts 3072 --seed <1000 + order_index>`: 48 periods; eight 1,024-token prompts beside 56 decodes are 8,248 tokens, so the same cut applies, and the stepping gives 12,297 steps, 471 with prompt tokens; 11,826 x 12.29 ms = 145 s of decode-only steps, 3,072 x 1,024 / 8,136 = 387 full steps' worth of prompt tokens at 92.3 ms, 36 s, and about 84 x 12.29 ms = 1 s for the rest: about 182 s. Random prompts share no prefix (`--random-prefix-len` defaults to 0), and `--random-range-ratio` defaults to 0, so every prompt has exactly the stated lengths. GuideLLM, which `run_loop.sh` uses (`guide`, `run_loop.sh:56-63`), reports a different ITL: each request's average gap, (last token - first token) / (output tokens - 1), with percentiles over requests weighted by output tokens (read at GuideLLM main, `schemas/base/request_stats.py:337-354`, `benchmark/schemas/metrics.py:1466-1470`; the pod installs it unpinned). Arithmetic for the headline row, in three parts.

**The cache read.** The core reads 64 x 4,352 entries x 61 layers per rank per step. At 1,152 B that is 19.57 GB, or 2.447 ms at 8 TB/s; at 576 B it is 1.223 ms. The step floor falls from 11.017 to 9.794 ms.

**The extra kernels.** Inputs: 64 sequences; 8 query heads per rank (64 heads at TP8, `gitm/planner/models/kimi-k2.5.yaml:34`), padded to 16 for the asm kernel; 576 query elements per head (512 latent plus 64 RoPE, `:36-38`); 512 output elements per head; 61 layers; 8.0 TB/s; the planner's launch floor of 2 µs (`HardwareSpec.kernel_launch_overhead_s`) and mid-band efficiency 0.75 (`eff_lo` 0.55, `eff_hi` 0.95).

1. The query per layer is 64 x 8 x 576 = 294,912 elements.
2. The concat-and-quantise reads it as bf16 (589,824 B) and writes fp8 (294,912 B). That is 884,736 B, or 0.111 µs at 8 TB/s, under the 2 µs floor, so the kernel costs 2 µs. It is one kernel on the loop's config, by vLLM v0.29.0's dispatch. `_DecodeConcatQuantFP8` is a `CustomOp` built with `compile_native=True` (`mla_attention.py:641-645`). A disabled custom op runs `forward_native` through `torch.compile` (`model_executor/custom_op.py:191-194`, `:209-269`), which for this op is the cat, the scale and the cast together (`mla_attention.py:1426-1443`; static per-tensor quantise in `quantization/input_quant_fp8.py:181-228`). An op is enabled only if `compilation_config.custom_ops` holds `all` or `+mla_decode_concat_quant_fp8` (`custom_op.py:285-293`, `:296-311`). With no `custom_ops` given, vLLM adds `none` when the backend is Inductor and compilation is on (`config/vllm.py:1444-1451`). The loop passes no `-O` level and no compilation config (`deploy/k8s/mi355x-kimi-loop.yaml`), so the level is the default 2 (`config/vllm.py:419`), the mode is VLLM_COMPILE (`:1431-1435`) and the backend is the platform's, Inductor (`config/compilation.py:1066-1067`; ROCm keeps the default `simple_compile_backend = "inductor"`, `platforms/interface.py:165`, `:248-252`). ROCm's platform defaults add `+quant_fp8`, `+grouped_topk` and `+sparse_attn_indexer` only (`platforms/rocm.py:866-894`), none of them this op. So the op is disabled, `forward_native` is compiled by Inductor, and the cat, scale, clamp and cast should fuse into one Triton kernel. If the op were enabled instead, `forward_hip` would run `torch.cat` and then AITER's per-tensor quantise (`quantization/input_quant_fp8.py:137-160`), two kernels: 61 more launches, 0.163 ms on the measured basis, which would move the headline band down by about 1.1 points. Pre-run check 3 counts them, and applicability 7 refuses the configs that enable the op.
3. The 8 to 16 head pad reads 294,912 B of fp8 and writes 589,824 B. That is again 0.111 µs, so 2 µs.
4. The split-KV partials. `get_mla_metadata_v1` builds AITER's persistent schedule on 256 work slots, one per CU (`aiter:csrc/kernels/mla/metadata/v1_2_device.cuh:847`, `:901-903`; vLLM's call passes page size 1 and KV granularity 16, `rocm_aiter_mla.py:1053-1077`). Phase 1 of the planner kernel (`v1_2_device.cuh:121-208`) charges each sequence its 16-token blocks plus 16 blocks of overhead (`:929`). At exactly 4,352 tokens that is 64 x (4,352 / 16 + 16) = 64 x 288 = 18,432 blocks. Each slot gets ceil(18,432 / 256) + 16 = 88, of which 72 are KV blocks (`:139-140`). The first sequence fills slot 0 with 72 of its 272 blocks, then needs ceil(200 / 72) = 3 fresh slots, and leaves slot 3 with 88 - (56 + 16) = 16, exactly the overhead, so the next sequence starts on a fresh slot. Every sequence therefore spans 4 slots: 4 partial tiles per sequence, 256 in all (`:200-204`; `_aiter_partial_tiles` in the code, pinned by a test). That alignment is the best case. One token more (4,353) gives 273 blocks, the boundaries fall inside slots, and the count is 313. The count takes every step's 64 sequences at one cache length L, 4,097 to 4,607 over a request's 511 decode steps (vLLM writes the step's own token to the cache before attention, `mla_attention.py:703-713`, `:725-733`). The schedule gives 256 to 317 tiles across those steps, 153,472 in all, so the mean is 153,472 / 511 = **300.34 tiles per step** (`_h002_mean_tiles`; an independent transcription of phase 1 gives the same count at every L). The stagger of up to about 40 tokens between the sequences in a step is ignored; the sensitivity below bounds it. Each tile holds 16 heads x 512 fp32 outputs plus 16 fp32 LSEs (`aiter:aiter/mla.py:607-616`): 32,832 B. Stage 1 writes 300.34 x 32,832 = 9,860,651 B per layer, 1.233 µs at 8 TB/s. These writes are stage 1's own traffic, so they are priced inside the fp8 kernel: its floor per step is the 1.2233 ms cache read plus 61 x 1.233 µs = 0.0752 ms of writes, 1.2985 ms, divided by the fp8 kernel's efficiency at each end of the band. `mla_reduce_v1` reads the partials back and writes the bf16 output, 64 x 16 x 512 x 2 = 1,048,576 B (`aiter:aiter/mla.py:684-694`): 10,909,227 B, 1.364 µs. A kernel costs the larger of its traffic and its launch (`gitm/planner/roofline.py:1349`), so the reduce still costs its 2 µs launch and adds nothing more.
5. `get_mla_metadata_v1` builds the schedule once per step, not per layer (`rocm_aiter_mla.py:1053-1077`): 2 µs.
6. Per layer that is 3 x 2 + 1.233 = 7.23 µs of floor, about 36% of the fp8 core's 1.2233 ms / 61 = 20.05 µs floor per layer.
7. Per step it is (3 x 61 + 1) = 184 launches x 2 µs = 0.368 ms, plus 0.075 ms of partial writes: 0.443 ms of floor.
8. The launches on the measured basis are 0.368 / 0.75 = **0.4907 ms** per step. The planner floors every node at the 2 µs launch, and the unchanged rest of the step is divided by 0.75 below, so the launches are divided by 0.75 too. The same 0.4907 ms is charged at lo, mean and hi: the kernels sit on the stream around attention, so nothing hides them. The writes ride with the fp8 kernel: 0.0752 ms / 0.55 / 0.75 / 0.95 = 0.137 / 0.100 / 0.079 ms at lo / mean / hi. At the mean the fp8-only work is 0.491 + 0.100 = 0.591 ms.

**The band.** The unchanged rest of the step is (11.017 - 2.447) / 0.75 = 11.427 ms on the measured basis. Each end puts the bf16 kernel at one efficiency and the fp8 kernel at another:

| End | bf16 core | fp8 core | Saved | Baseline step | ITL reduction |
|---|---|---|---|---|---:|
| mean | 2.4466 / 0.75 = 3.2621 | (1.2233 + 0.0752) / 0.75 = 1.7313 | 3.2621 - 1.7313 - 0.4907 = 1.0401 ms | 11.427 + 3.2621 = 14.690 ms | **7.08%** |
| lo | 2.4466 / 0.95 = 2.5754 | (1.2233 + 0.0752) / 0.55 = 2.3609 | 2.5754 - 2.3609 - 0.4907 = -0.2762 ms | 11.427 + 2.5754 = 14.003 ms | **-1.97%** |
| hi | 2.4466 / 0.55 = 4.4483 | (1.2233 + 0.0752) / 0.95 = 1.3668 | 4.4483 - 1.3668 - 0.4907 = 2.5909 ms | 11.427 + 4.4483 = 15.876 ms | **16.32%** |

The fp8 core column includes the partial writes; 0.4907 ms is the launches. Sums use unrounded terms, so the last digit can differ by one.

`H002.predict` prints each of these steps in `Prediction.arithmetic`.

**Sensitivity (estimated).** If the attention region ran outside a captured graph, each launch would cost about 5 µs (the eager figure in `HardwareSpec`). With the extra kernels alone at 5 µs (184 x 5 µs / 0.75 = 1.227 ms per step, the writes unchanged) and the rest unchanged, the headline band would be -7.23% / 2.07% / 11.68%. Applicability 6 refuses eager and no-graph configs for that reason. At v0.29.0 steady decode at 64 sequences runs one full HIP graph (`config/vllm.py:301`; `ROCM_AITER_MLA` reports `UNIFORM_BATCH`, `rocm_aiter_mla.py:347`), so 2 µs is used.

**Sensitivity (estimated): the tile count.** The registered band uses the window mean, 300.34 tiles. At the aligned best case, 256 tiles (every step at exactly 4,352 tokens; what `H002.predict` gives without request lengths), the headline band is -1.83% / 7.18% / 16.39%. At the worst step in the window, 317 tiles, it is -2.03% / 7.04% / 16.29%; 2,000 draws of 64 ragged lengths uniform in 4,097 to 4,608 gave 288 to 318 tiles (mean 306), inside the same range, so the stagger within a step moves the band by less than 0.2 points. At 317 tiles the reduce moves 11.46 MB, 1.43 µs, still under its launch. The observable is a median, not a mean: modelling each step's time at mean efficiency over the 511 window lengths and taking the median gives 7.084% against the registered mean's 7.081%, because the cache read grows by 0.75 µs per token across the window and dominates the tile jitter. The schedule build runs in the metadata builder, outside the captured graph (`rocm_aiter_mla.py:1086-1088`), so its one launch per step is nearer 5 µs; that adds 0.004 ms and is left out.

The kernel's own time, with stage 1's partial writes counted in the fp8 kernel, falls by 46.9% at the mean and by 8.3% to 69.3% across the band. The covered-op figure that `expected_delta_*` carries on the emitted spec is that, less the launches as a share of the bf16 kernel's time at each end: -10.7% / 31.9% / 58.2% at the headline. It carries them because `replay.predict_delta` multiplies the figure by the trace's attention coverage, and the extra kernels have no coverage of their own.

Replay runs on the baseline trace, so it credits only the baseline's cache-reading decode kernel. `kernel_scope` holds substrings of kernel names read from source: `mla_gluon` (MI355X bf16 at 8 heads), `mla_a16w16` and `mla_dec_stage1` (AITER's bf16 asm kernels, for 16 or more heads per rank), `mla_a8w8` (AITER's fp8 asm kernels), `splitkv_mla_kernel` (both FlashMLA kernels) and `Sm100FmhaMlaKernel` (CUTLASS MLA). No reduce, combine or cache-insert kernel matches: none reads the cached KV bytes that fp8 halves. Two baselines are not covered yet. H200's default bf16 kernel is FA3's `FlashAttnFwdSm90`, which prefill also runs, so crediting it needs op identity (`range_op`), not a name. B200's FlashInfer MLA kernel names come from downloaded cubins, not source. Until those are fixed, H-002's replay coverage on an H200 or B200 baseline trace is 0.

The `rag` point fits comfortably. The fit ledger (`memory_fit`, the loop's 0.92 utilisation, 4.5 GB workspace) leaves 184 GB per MI355X rank for KV, and the bf16 cache needs 19.6 GB.

   1. In the gitm sidecar, switch to arm B (`bash arm.sh B`), start one traced window (`python -m gitm.cli capture attach --port 8000 --duration 190 --out "$D/cap_B_precheck"`, the same call as `capture_window`, `run_loop.sh:84-86`), and drive the headline load with the Observable's `rag` command.
   2. From that window take t_A, in microseconds, the mean duration of `_mla_gluon` per launch (one launch per layer per decode step). The kernel's own GPU duration is used, not step time, which the tracer slows. If the window's mean cached tokens per sequence L differs from 4,352, scale t_A by 4,352 / L (the kernel's bytes are proportional to L).
   3. Compare t_A with the code's line `bf16 core per layer` in `Prediction.arithmetic`. At the headline: floor 2.4466 ms / 61 = 40.1 µs; at eff 0.95 / 0.75 / 0.55 = 42.2 / 53.5 / 72.9 µs.
   4. If 42.2 µs <= t_A <= 72.9 µs, the registered band stands. Go on to step 3.
   5. If t_A > 72.9 µs, or 40.1 µs < t_A < 42.2 µs, the band's bf16-efficiency assumption is broken. Re-derive the band from t_A with `gitm.agents.hypotheses.rederive_h002(w, t_A)`, with t_A in microseconds and `w` the baseline arm's workload (the function refuses any workload `H002.applies` refuses: arm L's fp8 cache, arm C's `--enforce-eager`, speculative decoding, context or data parallelism, a partly fp8 cache; and any baseline whose bf16 decode is not one `_mla_gluon` launch per layer: 16 or more heads per rank, H200, B200), and record the measured bf16 efficiency 40.1 µs / t_A. The function also refuses two kinds of value, and any refusal stops the run before any fp8-arm sample:
      - t_A at or below the 40.1 µs byte floor. That would be an efficiency above 1, which means the measurement (the wrong kernel, a mis-attributed launch, a unit) or the byte model (bytes per entry, cached tokens) is wrong. Find which before registering anything.
      - t_A more than 20 times the floor (above 802 µs, an efficiency under 0.05). That is most likely nanoseconds read as microseconds, or several launches summed.

      Then re-apply applicability 8 to the re-derived band: if its mean is under the measured noise floor, the hypothesis is not registered at this operating point, no fp8-arm sample is taken, and the run records the measured efficiency and stops. Otherwise register the new band and rejection-1 threshold under a new contract sha before any fp8-arm sample. The re-derivation keeps the bf16 core at the measured time at every end and leaves the fp8 kernel (with its partial writes), the launches and the rest of the step as registered:

      saved(e) = 61 x t_A - (F_fp8 + W) / e - X, ITL reduction(e) = saved(e) / (R + 61 x t_A), with e = 0.55 (lo), 0.75 (mean), 0.95 (hi),

      where F_fp8 + W = 1.2233 + 0.0752 = 1.2985 ms (the fp8 core's floor plus its partial writes), X = 0.4907 ms (the launches, measured basis) and R = 11.427 ms (the unchanged rest, measured basis). Example, t_A = 100 µs (eff 0.401): lo = (6.100 - 1.2985 / 0.55 - 0.4907) / (11.427 + 6.100) = 3.2484 / 17.527 = 18.53%; mean 22.13%; hi 24.20%. At t_A = 72.9 µs the re-derived hi equals the registered 16.32%. To print it from the worktree root:

      ```
      python -c "from gitm.agents.hypotheses import Workload, rederive_h002; from gitm.planner.context import hardware_spec_for, peak_for_sku; from gitm.planner.model_catalogue import load_spec; from gitm.planner.roofline import BatchConfig, ShardingConfig; w = Workload('kimi-k2.5', load_spec('kimi-k2.5'), hardware_spec_for(peak_for_sku('MI355X')), BatchConfig(batch=64, kv_cache_len=4352), ShardingConfig(tp=8), {'VLLM_ROCM_USE_AITER': '1'}, (4096, 512)); print(chr(10).join(rederive_h002(w, 100.0).arithmetic))"
      ```
3. **Load.** On arms A then L, time `rag` 4096/512 and `chat` 1024/256 at c=64, 3 repetitions each, with the Observable's `vllm bench serve` commands and `run_loop.sh`'s metrics scrape running alongside (`scrape_metrics`, `:65-71`).
4. **Correctness, before any keep decision.** With the server in arm L, run the correctness gate below, and compare it with the same runs on arm A. If arm L fails, restore with `arm.sh A`; the lever is rejected (rejection condition 4).
5. **Kernel plane.** `INTERVENTION='--kv-cache-dtype fp8' bash run_loop.sh e8` captures one traced window on arm B and one on arm I. Read each kernel's per-layer duration from them: `_mla_gluon` on arm B (it should repeat step 2's t_A); the quantise, the pad, stage 1 and the reduce on arm I, and the schedule build once per step. Then, with the server still in arm I, take the traced needle window the correctness gate asks for (Gates). Its timed runs are traced, so they are not the latency verdict.

On H200, a third arm, `--attention-backend FLASHMLA` with a bf16 cache (`engine/arg_utils.py:1021` at v0.29.0), separates the backend switch (FA3 to FlashMLA) from the cache dtype. It does not isolate byte-halving on one kernel. vLLM calls `flash_mla_with_kvcache` for bf16 and `flash_mla_with_kvcache_fp8` for fp8 (v0.27.1 `v1/attention/backends/mla/flashmla.py:317-342`). ## Gates

The loop's keep decision (`optimizer/apply.py`) measures throughput only, so a faster but wrong cache could be kept. `HypothesisProposer` therefore refuses to emit this candidate unless it is built with a `correctness_gate`, and the emitted `InterventionSpec` carries that gate in its `correctness_gate` field. `apply_intervention` runs it after measuring and before keeping, with whatever applicator the caller passed, so there is no wrapper to forget. A failing gate restores the change and puts the reason in `ApplyResult.error`. A gate that *crashes* (the benchmark times out, the server drops) is treated the same way: the change is restored and the error recorded as "not judged", because an unjudged candidate must never stay applied. A gate that returns no verdict within `safety.correctness_gate_timeout_s` is cut off and restored the same way; H-002 sets it to 90 minutes, twice the roughly 45 minutes its GSM8K and needle runs take on one arm (budget below). The callable is runtime-only and is lost when the spec is saved, so the spec also carries `safety.requires_correctness_gate`, and `apply_intervention` refuses a reloaded spec that lacks its gate. `tests/test_hypotheses.py::test_a_faster_but_wrong_candidate_is_rolled_back`, `::test_the_gate_is_on_the_spec_not_the_proposer` and `::test_a_saved_and_reloaded_h002_spec_is_refused_not_applied_ungated` pin that. The gate itself is the sentinel below; wiring it to lm-eval is the loop's job, not this spec's.

**Correctness.** Kimi K2.5 ships no `k_scale`/`v_scale`, so vLLM stores the cache at scale 1.0 and quantises the decode query at that scale too (`kv_cache.py:107-111`, `:129-136`; the server logs "Using KV cache scaling factor 1.0", `:146-148`). On this arm a prefill also runs in fp8 at scale 1.0, but only in a batch where no prefill has cached context (Mechanism). Prefix caching is on by default, so which gate prompts reach the fp8 prefill depends on cache hits, and the gate has to control them.

**Known blocker on the pinned image.** Two upstream defects sit on arm L's path, and neither is a scale effect. (1) The fp8 prefill unpad bug (Mechanism; vllm-project/vllm#60907, merged to vLLM main on 2026-10-14 as `e534024` and in no tagged release as of 2026-10-18, v0.32.0 included, so a main or nightly build after it carries the fix and the pinned v0.29.0 image does not): heads 4 to 7 are lost on every fp8 prefill with no context, which is exactly the prefill the needle gate drives on purpose, and most GSM8K prompts. (2) AITER's gfx950 a8w8 MLA decode kernels, including the `_ps` variant arm L runs on every decode step (`aiter:hsa/gfx950/mla/mla_asm.csv:9`), convert unscaled online-softmax numerators to E4M3 before P@V while the denominator stays fp32 (reported in ROCm/aiter#5535 and fixed by ROCm/aiter#6422, which covers more kernels and merged to AITER main on 2026-10-14 as `386e8f9`; it is in no tagged release as of 2026-10-18, the latest being v0.1.25, so v0.1.19 does not carry it). Probabilities below about e^-7 of the row maximum round to zero in the numerator but still count in the denominator, so diffuse attention under-weights the output (AITER's own fixture, one logit at 0 and 2,047 at -7, returns 0.35 against 1.0). Calibrated k/v scales touch neither step, so `--kv-cache-dtype-skip-layers` or a checkpoint with scales would not fix a failure either one causes. On the pinned image a gate failure is therefore expected, and it is recorded as blocked by these defects, not as a scale result (rejection 4). An arm-L correctness result means something only on an image with the prefill fix (a vLLM main or nightly build after `e534024`) and an AITER build after `386e8f9` (or a team decision to judge the gate with the decode defect in place); that image changes the pinned versions, so pre-run check 1 and the kernel names in check 3 are re-read against it first.

**A defect on the baseline arm's own kernel.** On the pinned AITER v0.1.19, `_mla_gluon` loads KV without bounds masks whenever the per-layer cache is over 2 GB (`aiter:aiter/ops/triton/gluon/mla_gluon.py:956`; the unmasked `global_load_to_shared` calls at `:441`, `:452`, `:467`, `:504`, `:519`, `:541`, `:597` and `:607`), which ROCm/aiter#5648 masked on 2026-09-25 (`32fc881`, after the pinned tag) after an illegal memory access at decode warmup on Kimi-K2.6 TP8 with a bf16 cache on gfx950. The loop's per-layer bf16 cache is about 184 GB / 61 = 3.0 GB, so arms A and B take that path on every decode step. The repo's own arm-A noise-floor run on this image completed 8 x 320 requests with 0 errors (`docs/autoresearch_noise_floor_mi355x.md`), so the fault did not reproduce here; whether the unmasked lanes ever reach the output is not established. It is recorded because arm A is the reference the gates compare arm L against and the arm step 2 measures: an arm-L-versus-arm-A gap is attributed to arm L's two defects only if arm A's own GSM8K and needle scores are sane.

Run on arms A and L:
- GSM8K (lm-eval-harness `gsm8k`, 5-shot, all 1,319 items, `local-completions` against the server). Arm L may not score more than 1.0 point below arm A. This checks decode numerics (on an image with the AITER fix above; on the pinned image defect 2 sits under it); its prefill coverage is not controlled. lm-eval's default `gsm8k` draws a random 5-shot set per question (its default `ContextSampler`, read at lm-eval main, not at the team's pinned version), so most prompts start differently. Two prompts whose first exemplar is the same share whole 16-token blocks, though, and one hit sends its whole batch to bf16 prefill. With a fixed exemplar set (`first_n`), a chat template or a shared system prompt, every prompt after the first hits the cache and runs bf16 prefill.
- Needle retrieval, the fp8-prefill part of the gate. 100 prompts, sent one at a time (concurrency 1) on arms A and L. Arm L may not score more than 2 points below arm A. Serial and short, because vLLM v0.29.0 runs the fp8 prefill only in a batch where no prefill has context: the builder makes its metadata only when `chunked_context` is None (`rocm_aiter_mla.py:1147-1152`), `forward_mha` sends the whole batch to the bf16 `flash_attn_varlen_func` path when it is not (`:1676-1688`), and it is None only when no prefill in the batch has any context (`mla_attention.py:1917-1919`). The scheduler serves running requests first (`v1/core/sched/scheduler.py:550-552`) and then gives a waiting prompt the smaller of its tokens and the budget left (`:954`, `:998`); the loop serves with `--max-num-batched-tokens 8192` (`deploy/k8s/mi355x-kimi-loop.yaml:159`). A prompt longer than what is left of the budget is chunked, its later chunks carry context and run bf16, and so does every prefill batched with them. With 100 prompts in flight that is nearly every prompt. So each prompt is at most 8,000 tokens by the model's tokenizer: one prompt alone fits the 8,192-token budget, and the 192-token margin keeps a decode token from a request still finishing from splitting it. Each prompt also carries its own haystack from the first token and goes to the completions endpoint with no shared template or system prompt, so no first 16-token block is cached. The loop's `long` context is 8,192 tokens; 8,000 is the longest that fits one step with that margin.
- Verify the fp8 prefill ran, by kernel name, in a traced window. On arm I (Experiment step 5), send the first 10 needle prompts the same way, one at a time, inside one traced window. AITER's fp8 prefill is `mla_pfl_qh192_vh128_m32x8_n128x1_causal1` (`aiter:hsa/gfx950/mla/mla_asm.csv:28`: fp8 q and kv, persistent, prefill, causal), picked by `mla_prefill_ps_asm_fwd` (`aiter:csrc/py_itfs_cu/asm_mla.cu:1153-1158`), which vLLM calls causal (`rocm_aiter_mla.py:1598-1610`), then `kn_mla_reduce_v1` or `kn_mla_reduce_v1_ps` (`aiter:csrc/kernels/mla/reduce.cu:1128-1141`, via `mla_reduce_v1`, `rocm_aiter_mla.py:1619-1631`). Each prompt prefills in one step, so the window must show `mla_pfl_qh192_vh128_m32x8_n128x1_causal1` 61 times per prompt, once per layer: 610 for 10 prompts. Fewer means a prompt or a chunk took the bf16 path, and the gate has not exercised the fp8 prefill. The reduce cannot confirm it, because fp8 decode runs the same reduce every layer. Arm L is the same server and scheduler without the tracer, so its serial runs take the same path.
- What `vllm:prefix_cache_hits` (`v1/metrics/loggers.py:595-596`) can and cannot show. It counts prompt tokens served from the prefix cache. If it does not rise over the needle run on arm L, no prompt took context from an earlier prompt's cached blocks. It cannot show that a prompt was not chunked (a later chunk's context is its own earlier chunk, not a cache hit), that a prompt did not share a step with another request's context-carrying prefill, or which kernel ran. Only the traced kernel count shows those.

**Latency.** Arm L's TTFT p50 may not rise more than 5% over arm A's, both at the c=64 load and on the serial needle runs. At c=64 which prefill steps take the fp8 path depends on how prompts land in steps as slots turn over: a step whose prompts all start fresh (including the first chunk of a prompt that is then cut) runs fp8, and a step that carries a cut prompt's tail runs bf16 for the whole batch. Stepping the budget rule over the run (Observable) gives 191 of the 708 prompt-carrying steps on the fp8 path, so the c=64 TTFT mixes the two; the serial needle runs are the controlled TTFT check on the fp8 prefill. Arm L's ITL p99 may not exceed arm A's by more than the noise floor.

## Rejection conditions

1. **Effect.** The registered efficiency band predicts an ITL change of -1.97% to 16.32% at the headline, positive meaning faster. The low end is a regression: at the band's worst pair of efficiencies the fp8 arm is 1.97% slower. So rejection 1 reads: if the observed reduction is below -1.97% minus the noise floor, that is, if arm L is slower than arm A by more than 1.97% plus the noise floor, reject at this operating point. A result of zero, or a slowdown inside 1.97% plus noise, does not reject on effect, because the band allows it. This threshold is fixed from the registered band (or from the re-registered one, if the pre-candidate check in Experiment step 2 fired); do not raise or lower it based on the observed result or replay estimate. Effect alone cannot reject a lever that does nothing, so conditions 2 and 3 carry the mechanism.
2. **Mechanism.** The two arms run different kernels, so kernel time alone cannot isolate the byte mechanism (the same reasoning as H-001's rejection 2). Compare `_mla_gluon` on arm B against `mla_a8w8_qh16_qseqlen1_gqaratio16_ps` on arm I, per layer. At plain decode arm B runs no reduce (one KV split), so `_mla_gluon` alone is the bf16 op; on arm I, `mla_reduce_v1` is one of the priced extra kernels, so the op is stage 1 alone and the reduce, pad, quantise and schedule build are each checked against their 2 µs launch floor. Agree this op definition with P1's owner beforehand. If the fp8 kernel's time is not below the bf16 kernel's by at least 8.3% (the band's worst case for stage 1 with its partial writes, kernel alone), the fp8 kernel is less efficient than the bf16 one by more than the band allows, and the measured pair of efficiencies replaces the band for this node. If the byte reduction is not seen in `vllm:kv_cache_usage_perc` (the fp8 arm should show half the occupancy for the same load), the layout assumption is wrong. That metric is v0.29.0's name (`v1/metrics/loggers.py:562`); `run_loop.sh`'s scrape records it from this branch on.
3. **Scaling.** A ratio of the `rag` and `chat` savings is the wrong test once the fp8 arm carries a fixed per-step cost: even at the mean the `chat` saving is negative (-0.151 ms against 1.040 ms at `rag`), so the ratio is undefined, not the 3.8x of the cache bytes alone. Fit the measured saving (ms per step, arm A minus arm L) against cached tokens over the two points at c=64 instead: saving = slope x tokens + intercept. The line through the two predicted savings at each end has a slope of 0.077 / 0.372 / 0.724 µs per cached token and an intercept of -0.612 / -0.580 / -0.561 ms (lo / mean / hi; from the unrounded savings, -0.276186 and -0.523454 ms at lo). The slope is mostly the halved core per token at 64 sequences on the measured basis; the partial writes shift both a little, because the window-mean tile count is 276.27 at `chat` and 300.34 at `rag` and the writes are priced at the fp8 kernel's efficiency at each end. Check at the mean: 0.3723 µs x 4,352 - 0.580 ms = 1.040 ms and 0.3723 µs x 1,152 - 0.580 ms = -0.151 ms, the two mean savings. If the slope is below 0.077 µs per token by more than its noise, the saving is not cache traffic. If the intercept is more negative than -0.612 ms by more than its noise, the fp8 arm adds more fixed work per step than the 184 launches and partial writes priced here.
4. **Correctness.** On an image that still carries either upstream defect in Gates, a gate failure is recorded as blocked, not as a rejection, and says nothing about scales. On an image with the prefill fix and a decode kernel the team has agreed to judge against (a fixed AITER, or the pinned one with its defect accepted as AITER's intended numerics), a gate failure rejects the lever for this family with uncalibrated scales on that kernel. `--calculate-kv-scales` no longer exists at v0.29.0. Reconsider it with `--kv-cache-dtype-skip-layers`, which keeps the named layers' cache at the model dtype (`engine/arg_utils.py:1299`, applied to MLA at `mla_attention.py:452-456`), or with a checkpoint that ships scales. A partly fp8 cache is a different prediction and must be re-derived before it runs.
5. **Above the band.** The band is the range of outcomes this mechanism explains. An observed reduction above its hi end (16.32%, or the re-registered hi) by more than the noise floor does not support the claim. Record it as outside the band, read every kernel's duration from the traced windows, and re-derive before any claim. The pre-candidate check exists so that the known cause, an under-filled bf16 kernel, is priced before the run instead of being found after it.

## What each outcome changes

- **Supported.** The catalogue entry `kv_cache_dtype_fp8` in `gitm/kernels/library.yaml` gets a hardware gate that includes MI355X, H200 and B200. Today it lists only A100, H100 and L40S, and the gate matches by substring, so it never fires on this team's hardware. Its flat 6% becomes this derivation. The measured AITER MLA efficiency replaces the band for that node on MI355X.
- **Pre-candidate check fires.** The band is re-registered from the measured `_mla_gluon` time before any fp8 sample, and the run is judged against it. Record the measured bf16 efficiency. The part of the saving that comes from leaving the bf16 kernel's one-split grid is then priced, not credited to the cache bytes; a bf16-side fix (vLLM passing a real `min_kv_seq_len` to Gluon) would be its own hypothesis.
- **Above the band (rejection 5).** Not supported. Re-derive before any claim.
- **Rejected on mechanism.** Record a scoped exclusion for AITER MLA fp8 on gfx950 at this head size, pinned by the measured kernel time.
- **Blocked on the image.** The gate result is recorded against vllm-project/vllm#60907 and ROCm/aiter#6422, no rule is added, and the run waits for an image that carries both fixes, or for the team's call to judge the gate without the decode fix.
- **Rejected on correctness (on an image with the prefill fix and an agreed decode kernel).** An applicability rule: fp8 cache on this family only with calibrated scales.
